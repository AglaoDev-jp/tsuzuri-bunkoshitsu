# toolsフォルダーの役割と使い方

この文書は、「綴り文庫室」の速度改善・音声先読み・計測機能の開発で用意した補助スクリプトについて説明します。`docs/tools_guide.md`として置くことを想定しています。関連する自動テストの説明は、[testsフォルダーの説明](tests_guide.md)を参照してください。


## 1. toolsは何のためにあるか

`tools`は、開発者が必要なときに実行する、診断・計測結果確認用のフォルダーです。現在は2本あり、関連する単体音声診断は `tests/diagnose_voicevox.py` にあります。3本ともゲーム起動時に自動実行するものではありません。

| スクリプト | 作成した目的 | 実行時に行うこと |
| --- | --- | --- |
| `summarize_performance.py` | 待ち時間の内訳を、人が読みやすい日本語で確認する | 保存済みの計測ログを読み、操作ごとの経過を表示する |
| `diagnose_ollama.py` | 接続先による遅延差と、モデルの登録情報を調べる | Ollamaの軽量APIへ接続し、接続時間や任意のモデル情報を表示する |
| `tests/diagnose_voicevox.py` | ゲーム内外で同じ条件の音声合成を比較する | 固定文をVOICEVOXで繰り返し合成し、内訳を表示・記録する |

これらを置くだけでゲームが速くなるわけではありません。どこに時間がかかっているかを見分け、改善前後を比較するための道具です。

## 2. 今回の開発での位置付けと、実行記録の扱い

速度改善では、LLMの出力速度だけでなく、要約の別生成、通信、先頭音声の準備、表示開始までの待ち時間を分けて確認する必要がありました。そのため、次の役割を用意しました。

1. ゲーム側の`src/performance_monitor.py`が、通常プレイ中の計測イベントをJSON Lines形式で保存する。
2. `summarize_performance.py`が、そのログを操作ごとに読み解ける形へ整える。
3. 接続自体の遅延を切り分ける場合は`diagnose_ollama.py`、音声合成だけを切り分ける場合は`diagnose_voicevox.py`を使う。
4. `tests`で、記録・表示・診断処理の正しさを、通信を代替した条件で確認する。

開発時には、通常プレイのログを使ってLLMの呼び出し回数、要約の採用方法、音声先読みの再利用、表示までの残り待ち時間を確認しました。集計スクリプトにも、要約・通常場面の先読み・音声診断・エンディングの先読みを判別する表示を追加しています。

ただし、**スクリプトを作成・テストしたことと、実機でそのスクリプトを実行したことは区別します**。公開整備前の提供ZIPには通常プレイの計測ログが1本あり、LLM呼び出しや音声先読みの記録はありますが、固定文の音声診断イベントはありません。`diagnose_ollama.py`は端末への表示のみで、実行履歴を自動保存しません。この資料だけから、両診断ツールを実機で実行済みとは判断できません。

## 3. 実行前の準備

以下のコマンド例は、プロジェクト直下、つまり`src`・`tools`・`tests`・`docs`が並ぶフォルダーで実行します。Windowsでも、ゲームに使っているPython環境から実行してください。

| スクリプト | 主な必要物 | サーバー起動 | 設定・ファイルへの影響 |
| --- | --- | --- | --- |
| `summarize_performance.py` | Python標準ライブラリ、保存済みログ | 不要 | ログの読み取りのみ |
| `diagnose_ollama.py` | Python、`requests` | Ollamaが必要 | 設定・モデル登録を書き換えない。結果は端末表示のみ |
| `diagnose_voicevox.py` | Python、`requests`・`pygame`など既存の音声モジュールの依存関係、ゲーム設定 | VOICEVOXが必要。Ollamaは不要 | 計測ログと一時WAVを作る。設定やゲーム用WAVキャッシュは変更しない |

音声診断は再生しませんが、共通の音声モジュールが`pygame`を読み込むため、インストールされている必要があります。ゲーム画面を起動する必要はありません。

## 4. summarize_performance.py：保存済みログの確認

### 目的と処理

計測ログは、1行につき1件のJSONを記録する`.jsonl`ファイルです。そのままでも読めますが、1回の操作について複数の処理が記録されるため、前後関係を追いにくくなります。

中心となる`summarize(path)`は、同じ`trace_id`、つまり同じ操作の識別番号を持つ記録をまとめ、日本語の説明へ変換します。ゲームやLLMを起動したり、測定をやり直したりする処理はありません。

### 使い方

最新の計測ログを読む場合：

```text
python tools/summarize_performance.py
```

特定のログを読む場合：

```text
python tools/summarize_performance.py "src/logs/performance_YYYYMMDD_HHMMSS_xxxxxxxx.jsonl"
```

後者のファイル名は書式例です。実際にある名前へ置き換えてください。

引数を省略すると、スクリプトの場所を基準に`src/logs/performance_*.jsonl`を探し、**ファイルの更新日時が最も新しいもの**を選びます。音声診断のログも同じ命名形式なので、診断直後にはゲームのプレイログではなく診断ログが選ばれる場合があります。比較ではパスを明示すると確実です。

### 主に確認できる内容

| 表示項目 | 確認すること |
| --- | --- |
| 場面・要約・追加エンディング・自由入力の設定整理 | どの目的でLLMを呼び、何回試したか |
| 呼出全体・ロード・入力処理・出力生成・tokens/s | モデルの生成と、それ以外の待ち時間を分ける手掛かり |
| HTTPとOllama内部時間の差 | 通信や処理境界の差を調べる手掛かり。差の原因を単独で確定する値ではない |
| 採用した要約・従来方式への復帰 | 場面と同時生成した要約を使えたか、別生成などへ戻ったか |
| 音声のクエリ・合成HTTP・保存・音声長・実時間比 | 音声準備のどの工程に時間がかかったか |
| キュー待ち・先読み準備・再利用・残り待ち | 先読みが表示前に間に合ったか |
| 本文表示開始・全文表示・キャンセル要求 | 操作開始から画面上の節目までの経過時間 |

### 読み方の注意

- 欠けた統計や不正な数値は、0秒ではなく「未取得」と表示します。
- 途中で切れたJSON行などはスキップし、スキップ数を表示します。ただし、ファイル自体を開けない場合などはエラーになります。
- LLM呼び出し全体に内部の生成時間が含まれるなど、測定範囲が重なる項目があります。すべてを足し合わせて総時間にはしません。
- 表示までの経過時間は操作の開始点からの値です。複数の表示区間や手動の続行を含む操作では、区間ごとの意味も合わせて確認します。
- 先読み時間が短くても、再利用された記録がなければ体感改善を確認したことにはなりません。
- 名前に「summarize」とありますが、**物語の要約をLLMで生成するツールではありません**。ログを整理して表示するだけです。
- 全プレイの平均・中央値を自動集計する統計レポートではなく、操作ごとの記録を表示するツールです。ログにある全イベントを逐一表示するものでもありません。

## 5. diagnose_ollama.py：接続とモデル登録情報の確認

### 目的と処理

`localhost`と`127.0.0.1`で、名前解決や接続試行などによる差が出るかを調べるために作成しました。あわせて、Thinking対応を検討する際にモデルの登録情報を確認できます。

主な関数は`compare_connections()`、`model_information()`、実行入口の`main()`です。

- `compare_connections()`は、`http://127.0.0.1:11434`と`http://localhost:11434`へ`GET /api/version`を送ります。
- 既定は各3回です。試行ごとに接続先の順番を逆にし、それぞれの時間・中央値と中央値の差を表示します。
- `--model`指定時は、追加で`POST /api/show`へモデル名を送り、`capabilities`・`thinking`・`details`・`parameters`を表示します。
- `--show-template`も指定すると、登録テンプレートを表示します。

文章生成、モデルのロード・アンロードを指示するAPI、モデルの登録変更は行いません。Gemma系でもLLM-jp系でも、登録されている名前を引数で渡す構成です。

### 使い方

接続だけを比較する場合：

```text
python tools/diagnose_ollama.py
```

モデル情報も確認する場合：

```text
python tools/diagnose_ollama.py --model "llm-jp-4.1-direct:latest" --samples 3
python tools/diagnose_ollama.py --model "gemma4:12b" --show-template
```

モデル名は実際の登録名に置き換えてください。

| オプション | 内容 |
| --- | --- |
| `--model` | 情報を確認する登録済みモデル名。省略時は接続比較のみ |
| `--base-url` | **モデル情報の取得先**。省略時は`src/data/game_settings.json`の`ollama.base_url`。読めない場合などは`http://127.0.0.1:11434` |
| `--samples` | 各接続先の試行数。1〜5、既定3 |
| `--show-template` | 登録テンプレートも表示する |

**`--base-url`を変えても、接続比較の2つのURLは変わりません。** 例えば別PCや別ポートを指定しても、接続比較は常にこのPCの11434番ポートを対象にします。指定した接続先で行うのは`/api/show`によるモデル情報の取得です。

### 判断できること・できないこと

接続比較は軽量APIの結果です。ここで差が出ても、物語生成全体が同じ秒数だけ短くなるとは断定できません。モデルの実際のtokens/sや、JSON出力の安定性は測りません。

また、`thinking`が「未提供」でも「推論しないモデル」とは判断できません。このツールは取得した登録情報を表示するだけで、Thinkingの有効・無効を切り替えたり、実際の生成による対応確認を行ったりしません。情報の返り方は、利用するOllamaと登録モデル側の対応にも左右されます。

現在の既定タイムアウトは各HTTP要求5秒です。自動リトライによる再送はなく、指定回数の比較を行います。接続比較で一部に失敗があっても、成功が1件以上あれば終了コード0になるため、終了コードだけでなく各行を確認してください。モデル情報の取得失敗時は1を返します。

## 6. diagnose_voicevox.py：固定文の音声合成計測

### 目的と処理

通常プレイでは場面ごとに文章が変わるため、音声合成時間の違いが、文章量によるものか、実行環境や同時処理によるものかを判断しにくくなります。このツールは、ゲーム内の「音声計測」と同じ固定文・共通処理を使い、比較条件をそろえるために作成しました。

`main()`が設定と引数を読み込み、`src/voice_diagnostics.py`の`run_diagnostic()`と`format_report()`を呼び出します。合成自体は、ゲームと共通の`VoicevoxClient`を使います。診断ロジックをツール側に別実装していません。

固定文は次のとおりです。識別名は`voice_probe_v1`です。

> 静かな図書室で、一冊の本を開きました。窓から柔らかな光が差し込み、次の物語が始まります。

### 使い方

VOICEVOXを起動したうえで実行します。

```text
python tests/diagnose_voicevox.py
python tests/diagnose_voicevox.py --speaker 3 --samples 3
```

| オプション | 内容 |
| --- | --- |
| `--speaker` | 話者・スタイルを指定するID。0以上。省略時は設定ファイルの`voicevox.speaker_id` |
| `--base-url` | 省略時は設定ファイルの`voicevox.base_url` |
| `--samples` | 試行数。1〜5、既定3 |

設定は`src/data/game_settings.json`から読みます。ゲーム画面で話者を変更した場合は、同じIDを`--speaker`で明示してください。このツールはゲーム画面の現在の入力値を直接読むわけではありません。

このスクリプトは引数の解析前に設定ファイルを読むため、`--base-url`や`--speaker`を指定する場合、また`--help`を使う場合も、設定ファイルが存在し、読み込める構成が必要です。

### 測る内容とファイルの扱い

1. エンジン版、対応デバイス、試行前の話者初期化状態を取得します。これらの情報が取得できなくても、合成の計測は続けます。
2. 同じ固定文を、既定3回合成します。正常時は1試行につき`POST /audio_query`と`POST /synthesis`の2回です。
3. クエリ、合成HTTP、WAV保存、音声の長さ、実時間比を記録します。
4. 最初の試行と繰り返しを分け、2回目以降の成功した合成HTTP時間の中央値も表示します。

各試行で別のキャッシュキーを使い、一時フォルダーにWAVを作るため、既存WAVの再利用による短い時間を合成速度として測ることを避けています。一時WAVは通常の終了処理で片付け、ゲーム用の音声キャッシュには混ぜません。**音声の再生はしません。**

計測ログは`src/logs/performance_*.jsonl`へ保存します。単体診断は通常プレイの計測ON/OFFとは別に記録を有効化します。ログ保存に失敗しても、合成結果を失敗扱いにする設計ではありません。

### 数値の意味と比較方法

実時間比（RTF）は、おおむね次の関係です。

```text
実時間比 = 合成HTTPにかかった秒数 ÷ 生成された音声の秒数
```

例えば、10秒の音声を5秒で合成した場合は0.5です。これは説明用の例で、実測結果ではありません。また、合成HTTPはエンジン側の待機・処理・転送を含み、GPUの演算時間だけを表す値ではありません。

比較する場合は、同じエンジン・話者ID・設定で、ゲーム開始前または終了演出完了後の「音声計測」と、この単体ツールを実行します。単体側ではゲームを閉じるなど、並行処理の条件もそろえて記録してください。通常の長い文章や先読み中の競合は、通常プレイのログと合わせて確認します。

- 「最初の試行」は、この診断での1回目という意味です。エンジンが既に動作済みなら、完全な初回起動の時間ではありません。
- 対応デバイスの情報は、実際にCPU/GPUのどちらで動作しているかを証明しません。ツールにも稼働モードは未確認と表示します。
- 同じ条件での反復比較のためのツールであり、固定文の結果だけで全場面の音声待ち時間を説明できるわけではありません。
- 合成エラー時は、同じ長い待ち時間を繰り返さないよう、その時点で後続試行を止めます。
- 中止は`Ctrl+C`です。通常は終了コード130を返し、完了済みの試行はログに残ります。正常な全試行成功は0、合成の失敗などは1です。

共通処理のHTTPタイムアウトは、メタデータ取得が各2秒、クエリが30秒、合成が60秒です。ゲーム内の中止ボタンは試行の境界で確認するため、進行中のHTTP要求を待つ場合があります。単体ツールの`Ctrl+C`とは中止の経路が異なります。

## 7. testsとの関係

`tools`と`tests`は、次のように役割を分けています。

| 種類 | 主な役割 | 実サーバーとの通信 | 結果が示すこと |
| --- | --- | --- | --- |
| 通常プレイと計測ログ | 実際のゲーム進行中の時間を記録する | あり | そのプレイ環境・条件で起きたこと |
| `tools`の診断スクリプト | 条件を絞って実環境を調べる | 診断2本はあり。ログ確認ツールはなし | 接続や固定文合成などの限られた条件での実測 |
| `tests`の自動テスト | 処理・記録・例外時の動作が期待どおりか確認する | 確認したテストでは通信を代替する | 記述した条件での正しさ。実機の速さや音質ではない |

ツールもコードなので、その動作自体をテストしています。

| 対象ツール | 関連するテスト | 主な確認内容 |
| --- | --- | --- |
| `summarize_performance.py` | `test_measurement.py`の`SummaryToolTests` | 欠けた統計・途中で切れた行を扱え、元のログを書き換えない |
| 同上 | `test_voice_prefetch.py` | 次場面の先読み・再利用・残り待ちを表示する |
| 同上 | `test_voice_diagnostics.py` | 固定文診断、実時間比、稼働モード未確認などを表示する |
| 同上 | `test_ending_prefetch.py` | エンディングと通常場面の先読みを区別する |
| `diagnose_ollama.py` | `test_summary_in_scene.py`の`ConnectionDiagnosticTests` | バージョン・モデル情報取得のAPIを使い、Thinking情報の欠落を誤解しない |
| `diagnose_voicevox.py`と共通診断処理 | `test_voice_diagnostics.py` | 引数の受け渡し、固定文・話者の一致、キャッシュ非依存、ログ、失敗・中止、一時ファイルの後処理など |
| ゲーム内診断の開始条件 | `test_ending_prefetch.py`の`DiagnosticGuardTests` | エンディング途中の先読みと診断を競合させない |

例えば、音声診断のテストではHTTP応答やWAVをテスト側で用意します。テストに合格しても、そのPCでVOICEVOXの実測が速いことや、実際のGPU動作を確認したことにはなりません。

全テストを実行する基本コマンドは次のとおりです。

```text
python -m unittest discover -s tests -v
```

テストには`tools`のファイルを直接読み込むものがあるため、テストを実行するときは`src`・`tests`・`tools`を一緒に保持してください。通常のゲーム起動にこれら3本の補助スクリプトは必須ではありませんが、削除すると関連テストや診断手順を使えなくなります。

## 8. diagnose_voicevox.pyの現在の配置

v4の提供ZIPでは `tools/` に2本、`tests/` に `diagnose_voicevox.py` があります。以前の本書は `tools/diagnose_voicevox.py` を前提としていましたが、現在のファイルは `tests/diagnose_voicevox.py` です。今回の整備ではファイルを移動せず、説明と実行コマンドを現状へ合わせました。

`test_voice_diagnostics.py` は `unittest discover -s tests` での実行時に、この診断ファイルを正常に読み込めます。将来配置を変える場合は、実行コマンドとテストからの参照も確認してください。ゲーム内の「音声計測」は `src/voice_diagnostics.py` の共通処理を使います。
