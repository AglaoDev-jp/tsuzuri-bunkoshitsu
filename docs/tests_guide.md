# testsフォルダーの役割と使い方

この文書は、「綴り文庫室」の速度改善・音声先読み・計測機能の開発で追加した自動テストについて説明します。2026年10月25日に確認した、5本の自動テストスクリプトを対象にしています。単体診断の `diagnose_voicevox.py` も現在は `tests/` にありますが、自動テストそのものではありません。

## 1. 何のために作ったものか

`tests`は、コードを変更したときに、期待している動作が保たれているかを自動で確認するためのフォルダーです。

今回の開発では、計測機能、要約の同時生成、音声の先読みなどを追加するたびに、次のような確認に使いました。

- 計測を追加しても、LLMへ送る生成条件が変わっていないか。
- 要約の生成回数を減らしても、正解・不正解・再挑戦の扱いが変わっていないか。
- 音声の先読みが、現在の読み上げを妨げたり重複合成を起こしたりしないか。
- 停止・再プレイの後に、古い音声や画面更新が戻ってこないか。
- 通信やログ保存が失敗しても、必要なエラー処理や進行ができるか。

既存機能を変更した結果、以前できていたことが壊れていないかを調べることを、**回帰テスト**と呼びます。このフォルダーには、新機能の確認と回帰テストの両方が含まれています。

ゲーム起動時に自動実行するものではなく、開発者が必要なときに実行します。確認したゲーム本体のコードから、これらのテストファイルを起動する処理はありません。

## 2. 今回の開発での使われ方

開発時は、おおむね次の順序で使用しました。

1. 既存の処理を確認し、維持したい条件をテストとして記述する。
2. 改善機能を実装する。
3. 正常な応答だけでなく、不正なJSON、通信失敗、キャンセルなども再現して確認する。
4. 追加したテストと以前のテストをまとめて実行する。
5. 不一致があれば実装やテストの前提を確認し、修正後に再実行する。

既存の開発記録にはv3.1.5で88件合格とあります。今回のv4公開前整備でも、**現在の配置を変更せず88件すべての合格を確認しました**。Linux・Python 3.12.14・requests 2.34.2・pygame 2.6.1を使用し、外部通信・実GUI・音声再生を代替した検証です。Windowsでの実プレイや実測速度を確認した結果ではありません。

「88件」はテストとして実行する確認単位の数です。88回の実プレイや、88種類のモデルを試したという意味ではありません。1件の中で複数の入力条件を試すものもあります。

## 3. 各スクリプトの内容

| ファイル | 件数 | 主な確認対象 |
| --- | ---: | --- |
| `test_measurement.py` | 22 | 計測追加前後の生成条件、JSON・通信エラー、ログ、ゲーム進行、先頭音声と本文の開始順 |
| `test_summary_in_scene.py` | 10 | 場面と要約の同時生成、採用条件、従来方式への復帰、呼び出し回数、接続診断 |
| `test_voice_prefetch.py` | 17 | 通常の次場面の先頭音声の先読み、キャッシュ再利用、待機共有、停止・終了 |
| `test_voice_diagnostics.py` | 20 | 固定文診断、音声の長さと合成実時間比、計測記録、診断画面と単体ツールの入口 |
| `test_ending_prefetch.py` | 19 | エンディングの先読み、表示順、手動続行、音声のない区間を挟んだ保持 |
| **合計** | **88** | 確認したソースに定義されているテスト数 |

### test_measurement.py

主に、計測機能を追加しても元の処理を変えていないことを確認します。

- モデル名を変えても、要求するJSON形式・Thinking指定・温度などを意図せず変えないこと。
- APIの統計が欠けていたり不正な値だったりしても、正常な返答を扱えること。
- 不正なJSON、空の返答、タイムアウト、キャンセルを適切に扱うこと。
- ログ保存に失敗しても生成結果を返せること。
- 複数スレッドが記録しても、ログの行や操作識別子が混ざらないこと。
- 従来形式の返答への対応、自由入力の開始処理、不正解・再挑戦を維持すること。
- 音声ONでは準備完了後に本文と音声を開始し、音声OFFや音声失敗時も本文を表示できること。
- 古い表示・生成結果を無視し、選択可能になる条件を維持すること。
- 統計の欠落や途中で切れたログを、表示ツールが読み取れる範囲で扱うこと。

このファイルの`response()`や`scene_data()`は、他のテストでも使う共通のテストデータ作成用関数です。

### test_summary_in_scene.py

要約の同時生成によって、物語の記憶や進行を壊さないことを確認します。

- 用意された要約は正解時だけ採用し、不正解・再挑戦で先に反映しないこと。
- 同時要約がすべて利用できる通常ジャンルの5場面クリアでは、呼び出しが6回になること。
- 要約の欠落・型の不一致・文字数超過では、場面全体を再生成せず、従来の別要約へ戻ること。
- 同時要約をOFFにした場合や最終場面の扱いを維持すること。
- キャンセルを通常の失敗として飲み込まないこと。
- 設定した接続先を計測処理が勝手に書き換えないこと。
- Ollama診断ツールの要求先や、対応情報がない場合の扱いが正しいこと。

ここで確認するのは、要約の採用ルールや形式上の条件です。生成された要約が物語の重要事項を十分に保持しているかを、自動で意味評価するテストではありません。

### test_voice_prefetch.py

通常の次場面の先頭音声を、現在の読み上げ中に準備する処理を確認します。

- 現在文の音声生成を先に処理し、次場面は先頭1チャンクだけを準備すること。
- 準備済みの音声を再利用し、同じ合成を重複して始めないこと。
- 準備途中で次へ進んだ場合、実行中の準備を共有して待てること。
- 停止・終了で未完了の先読みを取り消せること。
- キャッシュ削除後に戻った古い応答を、通常キャッシュへ再公開しないこと。
- 話者や文章が違う音声を再利用しないこと。
- 先読み失敗時は、表示時の通常準備へ戻れること。
- 読み上げOFF、先読みOFF、古い表示世代では先読みを開始しないこと。

一部の確認では実際のPythonスレッドを動かし、`threading.Event`で「合成の途中で停止する」といった処理順を制御しています。実サーバーの応答時間を待って再現する方式ではありません。

### test_voice_diagnostics.py

VOICEVOX診断が、比較条件をそろえて正しく記録・表示できるかを確認します。

- ゲーム内・単体の診断経路が、同じ固定文と話者を使うこと。
- 反復計測がWAVキャッシュ命中による計測にならないこと。
- 受け取ったWAVから音声長や合成実時間比を求められること。
- 音声長を取得できなくても、計測の都合で音声処理を失敗させないこと。
- 補助情報の取得失敗、合成失敗、中止、ログ保存失敗を扱えること。
- CUDA対応という情報だけで、実際にGPU使用中と判定しないこと。
- 生成キューの記録が、予約時の操作識別子に結び付いていること。
- 診断の二重起動、実行中のゲームへの割り込み、終了後の画面通知を防ぐこと。

このテストでは、長さが分かっている簡単なPCM WAVもテスト用に作成します。実際のVOICEVOXの合成速度を測定しているわけではありません。

### test_ending_prefetch.py

エンディングの音声先読みを追加しても、既存の見せ方や進行を維持できるかを確認します。

- GOOD END、エピローグ、GAME CLEAR、AIコメント、PLAY RECORD、最後の挨拶の表示順を維持すること。
- 文字と音声が完了しても自動で次へ進まず、続行操作を待つこと。
- 続行後の既存の500ms待機を維持すること。
- 音声のないPLAY RECORDを挟んでも、最後の挨拶の先読みを保持できること。
- 先読みした未来の文章を、先に画面やバックログへ出さないこと。
- 音声OFF、先読みOFF、話者変更、停止、終了、準備失敗を扱えること。
- 最初のGOOD ENDは通常の準備を使い、最後の挨拶からは追加の先読みを行わないこと。
- エンディング途中の先読みと、固定文診断を競合させないこと。

通常場面と共通する待機・中止の確認は、`test_voice_prefetch.py`のテストをエンディングの条件でも再利用しています。

## 4. 実サービスを使わずに確認する仕組み

テストにはPython標準の`unittest`と、`unittest.mock`の`Mock`・`patch`を使っています。

**モック**は、本物の通信や画面部品などの代わりに、テスト用の振る舞いを用意する仕組みです。

例えば、Ollamaへ本当に問い合わせる代わりに、決められたJSONを返すようにします。その状態で、ゲーム側のJSON解析、場面の検証、要約の採用、呼び出し回数などを確認します。HTTP応答のテストデータには、実際の`requests.Response`も使っています。

画面のテストではTkinterの実ウィンドウを作らず、部品や予約処理を代替します。音声のテストでも、実際にスピーカーから音を出す処理は代替します。一方、JSON解析、キュー操作、キャッシュへの書き込みなど、確認対象の処理は実コードを通します。

したがって、テスト内の`gemma4:12b`や`llm-jp-4.1-direct:latest`という名前は、要求内容や分岐を確認するための条件です。実モデルをロードして生成品質を試したことを意味しません。

## 5. 実行方法

ゲームを動かすPython環境を使い、`src`・`tests`・`tools`が並ぶプロジェクト直下で実行します。

```text
python -m unittest discover -s tests -v
```

特定のファイルだけを調べる場合は、例えば次のようにします。

```text
python -m unittest discover -s tests -p "test_voice_prefetch.py" -v
```

テスト間で共通関数や準備処理を参照しているため、特定のファイルだけ実行する場合も、他のテストファイルはそのまま置いてください。すべてのファイルに直接実行用の入口があるわけではないため、基本は上記の`unittest discover`を使います。

必要なものは、Python、ゲームが使う`requests`・`pygame`、およびGUI関連テストの読み込みに必要な`tkinter`です。テストのためだけに`pytest`を追加する必要はありません。確認したテストは外部通信を代替するので、OllamaやVOICEVOXのサーバー起動は不要です。

出力の主な意味は次のとおりです。

| 表示 | 意味 |
| --- | --- |
| `ok` | そのテストの確認条件を満たした |
| `OK` | 今回実行したテスト全体で失敗・エラーがなかった |
| `FAIL` | 期待値と実際の結果が一致しなかった |
| `ERROR` | 読み込み失敗や予期しない例外などで確認を完了できなかった |

`FAIL`や`ERROR`が出た場合は、表示されたテスト名と例外を確認します。ゲーム本体の問題だけでなく、必要なファイルやライブラリの不足、フォルダー移動による参照先の不一致でも発生します。

## 6. 必要なフォルダー構成と実行時のファイル

テストは、プロジェクト直下に`src`・`tests`・`tools`が並ぶ構成を前提にしています。各ファイルで、親フォルダーを基準に`src`や`tools`を検索対象へ加えているためです。

`tests`や`tools`を別の場所へ移す場合は、実行方法や参照先も合わせて確認する必要があります。

多くのログや音声キャッシュは一時フォルダーに作成し、テスト後に片付けます。ただし、`main`の読み込みに伴うフォルダー作成や、診断ツール入口の検証により、プロジェクトの`src/logs`・`src/voice_cache`、計測ログ等が作成される場合があります。テスト全体がファイルを一切作らないという意味ではありません。

ゲームの通常実行には`tests`自体は不要ですが、ソースを保守・改修する場合に再利用できる開発資料です。今後ゲーム仕様を意図して変更した際は、古い期待値が残っていないかテスト側も見直します。

## 7. 合格しても別途確認が必要なこと

自動テストの合格は、記述した条件で処理が期待どおりだったことを示します。ゲーム全体の品質や、すべての環境での動作を保証するものではありません。

次の内容は、実機でのプレイや計測で別途確認します。

- 物語の面白さ、日本語の自然さ、人物・設定・伏線の一貫性。
- 各LLM・Ollamaバージョンでの実際の出力と対応状況。
- 実際の生成速度、VRAM使用量、CPU/GPUの稼働状態。
- VOICEVOXの発音、音切れ、音量や音楽とのバランス。
- 実ウィンドウの見た目、配置、操作感、デバイス固有の問題。
- テストで再現していないタイミングでの競合や、長時間の連続動作。

`tests`は処理の正しさを自動確認するもの、`tools`の診断スクリプトは実環境の状況を調べるもの、通常プレイの計測ログは実際の操作にかかった時間を記録するもの、という役割の違いがあります。

## 8. v4公開前整備での構成確認

現在の提供ZIPには、自動テスト5本（実行時88件）と `tests/diagnose_voicevox.py` があります。以前の本書が案内していた `tools/diagnose_voicevox.py` はありませんが、ファイル自体の欠落ではなく配置の違いです。

`python -m unittest discover -s tests -v` は `tests/` もモジュール検索対象にするため、単体診断を読み込むテストも合格します。エンディングテスト19件のうち4件は既存のテストメソッドを別名で再利用しているため、`def test_` の文字列だけを数えると全体84件になります。実行時の88件との矛盾ではありません。

通常プレイにはtestsやtoolsは不要ですが、ソースの保守に役立つため、両方を公開対象として維持しています。既存の配置・テストコードは変更していません。単体診断の実行手順は [toolsフォルダーの説明](tools_guide.md)を参照してください。自動生成の型チェックキャッシュ、音声キャッシュ、ログは公開用ZIPに含めません。
