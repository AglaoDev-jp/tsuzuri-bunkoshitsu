# 綴り文庫室 v3.1.5 — エンディングの先頭音声を事前準備

> この文書はv3.1.5実装時の開発記録です。下記の「今回」、差分更新ZIP、実測値、検証環境は当時の内容を指し、v4公開前整備の結果ではありません。現在の起動・ビルド・設定は [README.md](../README.md)、最新のテスト結果と構成は [testsの説明](tests_guide.md)を参照してください。

添付された実プレイ後のv3.1.4を基準に、タスク2を実装しました。
通常場面で使っていた先頭1チャンクの事前準備を、エンディングにも適用しています。

## 更新方法

1. ゲームを終了して、現在のv3.1.4フォルダーをコピーしてください。
2. `tsuzuri_bunkoshitsu_v3.1.5_update.zip`を解凍し、中身をコピー先へ上書きします。
3. `src`同士、`tools`同士、`docs`同士、`tests`同士を重ねます。`src/src`のような二重階層にしないでください。
4. これまでと同じPythonで`src/main.py`を起動してください。既存exeは更新されません。

小容量の更新ZIPです。画像・音楽・設定ファイル・過去ログ・音声キャッシュは同梱しません。
設定ファイルは上書きしないため、お手元の接続先・音量等を維持できます。
回帰テストをまとめて同梱し、以前のOllama診断ツールも添付にない場合に補います。このツールの内容は前版と同一で、自動実行しません。

## 今回の動作

現在文の音声生成をすべて先にキューへ入れ、その後に次の音声区間の先頭1チャンクだけを準備します。
分割規則は従来どおり最大80文字です。合成ワーカーを増やさず、現在の読み上げを優先します。

| 表示・読み上げ中の区間 | 事前準備する音声 |
| --- | --- |
| GOOD END | エピローグの先頭 |
| エピローグ | クリアメッセージの先頭 |
| GAME CLEAR | AIコメントの先頭 |
| AIコメント | 最後の挨拶の先頭 |
| PLAY RECORD（音声なし） | AIコメント中に予約した最後の挨拶を保持。新たに重複予約しない |
| 最後の挨拶 | 先読みを追加しない |

表示順はGOOD END→エピローグ→GAME CLEAR→AIコメント→PLAY RECORD→最後の挨拶のままです。
各区間は文字と音声の完了後に続行ボタンを出し、押すまでは次へ進みません。
ボタンを押した後の既存の500ms待機、本文と音声をそろえて開始する演出、BGM・画像・効果音のタイミングも維持しています。
先読みした本文を画面やバックログへ早く出したり、音声を先に再生したりすることはありません。

最初のGOOD END自体は、これまでどおり表示時に先頭音声を準備します。
最終選択後のLLM生成やGOOD END表示開始までを短縮する実装ではありません。
次区間の残りの音声は、引き続きその区間の読み上げ中に生成します。

## 停止・変更・失敗した場合

- 音声停止・Enterによる音声中断では、未完了の先読みも取り消します。次の区間は必要なら通常準備へ戻ります。
- 「最初から」・生成キャンセル・終了でも、古い先読みが後から再生されないようにします。
- 実行中のHTTPそのものは強制終了しません。取消後の先読み結果は通常キャッシュへ公開しません。
- 話者や本文が変わった場合は、一致しない音声を使わず現在の条件で準備します。
- 読み上げOFFでは先読みも行いません。ON/OFFの扱いは次区間の表示準備時の設定に従います。
- 次へ進んだときに同じ先読みがまだ実行中なら、その完了を音声準備ワーカーで共有して重複合成を防ぎます。GUIでは待機しません。
- 先読みだけが失敗した場合は画面へエラーを追加せず、表示時の通常準備で再試行します。通常準備も失敗した場合は従来どおり音声エラーを表示し、本文を続けます。
- タスク1の固定文「音声計測」は、エンディング途中の先読みと競合させないため、最後の挨拶まで終了してから開始できます。ゲーム開始前も引き続き利用できます。

## 設定と比較

新しい設定は`voicevox.prefetch_ending_first_chunk`です。省略時もONとして動作するため、設定ファイルを変更せず試せます。

OFFで比較する場合は、`src/data/game_settings.json`の既存`voicevox`内へ次の項目を追加して再起動してください。
ほかの設定は消さず、前後の項目とカンマで区切ります。

```json
"prefetch_ending_first_chunk": false
```

ONへ戻す場合は`true`にします。従来の`prefetch_next_scene_first_chunk`とは独立しています。
片方の先読みをOFFにしても、もう片方を自動的にOFFにはしません。

読み上げをONにし、同じ話者・モデルで数プレイずつ比較してください。
エンディングの各読み上げを最後まで聞いてから続行すると、先読みが間に合うかを確認しやすくなります。
次に、音声停止やEnterで早く進む場合、区間間で話者を変更する場合も確認してください。
文章の長さが毎回異なるため、1回の差だけで改善率を決めないでください。

```text
python tools/summarize_performance.py src/logs/performance_対象ファイル.jsonl
```

既存の先読みイベントへ`prefetch_kind`を追加しました。`next_scene`は通常場面、`ending`はエンディングです。
`voice_audio.voice_role`にも`ending_prefetch`を追加し、日本語ログ表示で区別します。
起動ログに今回の先読みのON/OFF、アプリ版に`3.1.5`を記録します。

- `voice_prefetch_finished`：先頭音声を準備できたか、準備に何秒かかったか。
- `voice_prefetch_use`：同じIDの音声を次の区間で使ったか、残り何秒待ったか。
- `first_voice_prepared`：表示時の先頭音声準備にかかった時間。
- `display_started`：続行操作から実際の本文開始までの時間。

イベントは同じ時間範囲を含むため、単純にすべて足し合わせないでください。

## 効果の見込みとリスク

v3.1.4の通常プレイでは、未キャッシュの音声合成HTTPが平均約4.92秒でした。
今回も先頭音声の準備を直前の読み上げへ重ねられれば、続行後の待ちを減らせる可能性があります。
これはv3.1.5の実測短縮量ではありません。VOICEVOXの合成速度そのものや、CPU/GPU稼働モードは変えません。
タスク1のゲーム内外の固定文比較も、引き続き原因調査に利用できます。

- 現在文の合成が長い、音声停止してすぐ次へ進む等の場合は、準備が間に合わない・取り消されることがあります。
- 先読みをしてから進行をやめると、使わない音声の合成やディスク使用が増える場合があります。
- 合成が前の読み上げ中へ移るため、実機でのCPU/GPU負荷や音切れは確認が必要です。
- 完成済みキャッシュは従来どおり残します。話者変更等で未再生になった先読み音声も、生成済みWAVを対象とする音声保存に含まれる場合があります。
- 先読み失敗後に通常準備を試すため、その場合は通常より通信回数が増えることがあります。

LLMのプロンプト・Thinking設定・呼び出し回数・要約方式、分岐、物語本文、エンディングの内容・表示順は変更していません。
